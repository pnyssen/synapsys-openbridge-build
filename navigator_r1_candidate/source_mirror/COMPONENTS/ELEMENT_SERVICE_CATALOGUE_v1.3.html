SEMANTIC L3 · DESIGN PROBABLE · OPERATIONAL POTENTIAL

Purpose: Define the complete design inventory of Services and the governed relationships required to deliver context-specific Benefits and create persistent Assets.

Owns: Service identity, purpose, category, target Context, beneficiary, value proposition, lifecycle position and required relationships.

Does not own: Method substance, Pattern admission, canonical promotion, Benefit-realisation authority, Asset qualification or operational transaction data.

Boundary: design definitions and instance taxonomies only. Odoo remains operational truth. No operational metrics or mutable record detail is duplicated here.

Design attributes

Kinematics

Required integrations

Nine verbs applied to the Service Catalogue

Each verb governs the whole element and applies to any selected instance from any taxonomy category. Verbs are not owned by categories; primary Mesh anchors reflect where each verb most often operates.

VerbService-Catalogue-specific actionPrimary Mesh anchor
OrientIdentify the need, Context, beneficiary and current catalogue coverage before selecting or proposing any Service instance; test that the need is not already served.Signal
CanonicaliseResolve the Service code, name, category, boundary and authoritative basis; a Service listed here is a design definition — storage alone is never canon.Interpretation
StructureBind the selected instance to its Context, required Method/Pattern/Canonical references, Work Object, expected Benefit and potential Asset effect.Structuring
AssureTest MECE coverage across the nine categories, evidence freshness, authority state, design-vs-operational PPV separation and the instance's failure inversions.Validation
NavigateLocate the correct instance, its design definition here, its Odoo operational reference and its queue position — and state the one next valid gate.Validation → Action routing
ComposeAssemble complementary Service instances across categories into one governed engagement without double-counting scope, Benefits or beneficiaries.Structuring / Action
ActivateRelease exactly one authorised Service expression into a Work Object; every operational mutation stays D007-gated and is never triggered from this page.Action
TransformUse observed variance, exceptions and A/B evidence to refine, split, retire or recombine catalogue instances under authority.Learning / Asset Conversion
ProjectRender the current design catalogue, its freshness, gaps and boundaries — explicitly as projection, never as operational truth.Feedback

Context-specific Strategy → Benefit → Asset contract

1. Context

Select the exact ecosystem, enterprise, client, partner, program, project, market, platform or design Context.

2. Strategy

Select the named Strategy and state the causal contribution expected from this instance.

3. Instance

Select one taxonomy category and its permitted variation.

4. SMART Benefit

Name beneficiary, baseline, target, indicator, evidence source, attribution rule and decision date.

5. Asset

Name the persistent Asset class expected if the Benefit is evidenced and qualified.

6. PPV and authority

Record design PPV and operational PPV separately; progression remains evidence- and authority-gated.

Acceptance tests

  1. All nine design-instance categories are distinct and collectively cover the element design space.
  2. Each category defines purpose, attributes, variations, kinematics, integrations and MECE boundary.
  3. Each category can be selected for a specific Context.
  4. Each selected instance maps to a named Strategy, SMART Benefit and Asset class.
  5. Nine verbs and all Mesh stages are element-specific, not generic outcome text.
  6. No operational record detail is fabricated or duplicated from Odoo.
  7. No browser preview, network access, remote dependency, iframe or permission prompt is required.
Authority: design projection only. Canon, Pattern, Service, Method, Asset, Benefit-realisation and PPV movement remain held unless separately authorised.
Replay-validity: PRESERVED.

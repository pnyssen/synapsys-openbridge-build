## 2. What was built, and why a script and not an addon tool
release/rc07_service_catalogue_adoption/loader/service_catalogue_load.py (+ README.md). A standalone script, run by hand from `odoo-bin shell` after a backup and a reviewed dry-run, because it must never run on module upgrade, must not change the addon tree installed on dev, and should be reviewable and removable on its own.
- `run(env, extract, apply=False, name_rulings=None)`: DRY-RUN by default (prints the diff, writes nothing); `apply=True` writes; the caller commits. The command line is an offline plan only (no database, relations not checked) and has no apply switch.
- Idempotent: key v19_id; created rows are marked by external ids in the pseudo-module `__synapsys_v19_load__` (Odoo's own import convention), because synapsys.service has no batch field and none is added. A second apply changes 0 rows (proved by an empty write log). A row with the same v19_id that the loader did not create is reported CONFLICT_UNMARKED and never touched.
- Only managed fields are written; perspective, kind_proposed, ppv, kind, shape, verb and every computed slot are never written. A hand edit to a managed field shows as an UPDATE in the dry-run; fields outside the managed list are left alone.
- `rollback(env, apply=False)`: removes only the services and the Standard the loader created (by the external-id marker); a Standard still used by a row the loader did not create is kept; reference data is never touched.
- Reach: imports are only argparse, collections, hashlib, json, re, sys. It has no V19 connection; the models it names are synapsys.service, synapsys.service.standard, ir.model.data (writes) and synapsys.context, method, canon, pattern, domain (read only).

## 7. Gaps, findings and choices to review (mine, not rulings)
1. NAMES (R8). x_name is the "CODE name" display composite in V19 on 43 rows, so a literal equality test would hold all 49. I compare the two after removing a leading code and dash. They agree on 47. They DIFFER in substance on two rows, which are HELD: v19 id 3 (x_name "SC-03 Human-AI Orientation and Navigation" versus x_service_name "Human-AI Orientation and Navigation (HAION)") and v19 id 14 (x_name "SA-04 Partner Orchestration and Ecosystem Governance" versus x_service_name "Relationship, Partner & Collaborative Ecosystem Orchestration"). `name` is required, so those two rows are not created until the Steward rules a name (a one-line `name_rulings` entry per row). Decision needed: the two names.
2. On v19 ids 18, 34 and 35 x_service_name already begins with the code ("SC-06 Governance Advisory Board..."); I remove the code once so the screen does not show it twice. On id 43 the dash difference is ignored. Your call if you want x_service_name copied verbatim.
3. GAPS (R2). gap_html and gap_count are computed from the model's _gap_fields; they cannot be written. Context, Method, Canon, Pattern and Domain are not among _gap_fields, so an unresolved link shows only in the loader report (and the raw V19 pattern ids survive in pattern_codes), not on the Service screen. Showing them there needs a model change (extend _gap_fields): a ruling.
4. PROVIDER FALLBACK (R3). The Standard has no named field for it, but its generic paragraphs list can hold it, so I load it and record the reference under a key the model does not display (the model's inherited-text view lists only its nine CONTRACT fields). For the 18 rows whose fallback text differs there is no field at all, so that text stays only in the extract (held, counted: 18). A one-line model change would display it; not made.
5. THRESHOLD (R3). The contract says text "identical on a majority of rows", but its own counts (15 of 47, 15 of 49) are not majorities. I used "the most common exact text, shared by at least 10 rows", which gives exactly the contract's four groups. Two smaller shared groups exist (authority gate 6 rows, observation 5 rows) and stay as own text.
6. LIFECYCLE (R4). The model's own help text says lifecycle is "one status (v19 x_service_status), unchanged", while the contract maps future_scoped to candidate and deprecated to retired. Implemented as the contract says, flagged PROPOSED pending S3; changing it is one table.

Say if you want another form. x_steward_contact_id is not written: on every row that has it, the owner is the same person, so it adds nothing (checked), and the target was ambiguous.

9. Marker mechanism (external ids in `__synapsys_v19_load__`, noupdate) is the one thing the contract left open ("load-batch marker or the v19_id set"); it is unverified against a real database. The v19_id set alone could not tell a loader row from a hand-made one, which the conflict test needs.
